# AGENTS.md

Guidance for coding agents and contributors. User-facing documentation lives in [README.md](README.md), and the tests and manual checks in [TESTING.md](TESTING.md).

## Project overview

simulacra is a generative art program that draws abstract patterns and stylized representations of real phenomena: 48 styles, 24 palettes, PNG, APNG and GIF output, and a command line. `core/` is a Cargo workspace with `engine` (package `simulacra_engine`: scenes, shaders, palettes, noise; usable as a library) and `cli` (package `simulacra_cli`, the `simulacra` binary with its PNG, APNG and GIF writers). Third-party dependencies are allowed.

The program was ported pixel for pixel from a Python reference, so seeds reproduce CPython's random generator and arithmetic bit for bit. The reference is gone; committed portable fixtures and golden hashes now pin every style's output, and the arithmetic must be kept exactly (see "Exact arithmetic"). No styles are being added or changed for now.

## Commands

```bash
M="--manifest-path core/Cargo.toml"
cargo test $M && cargo clippy $M --all-targets -- -D warnings                      # whole workspace
cargo test $M -p simulacra_engine && cargo clippy $M -p simulacra_engine --all-targets -- -D warnings   # the engine on its own
cargo test $M -p simulacra_engine --features json   # also the portable fixtures and scene validation (fixtures.rs and validation.rs need json)
cargo clippy $M -p simulacra_engine --all-targets --features json -- -D warnings   # lints those two as well
cargo test $M -p simulacra_engine --features json --test fixtures -- --ignored --exact bless_fixtures   # regenerate changed fixtures (run alone, then the line above)
cargo build --release $M -p simulacra_cli && core/target/release/simulacra --style waves --out waves.png
sh core/cli/tests/golden.sh check core/target/release/simulacra   # the binary renders the golden hashes (add --container IMAGE to run it in a clean image)
DIR=$(mktemp -d)/golden; sh core/cli/tests/golden.sh check core/target/release/simulacra --keep "$DIR"; SIMULACRA_GOLDEN_OUT="$DIR" cargo test --release $M -p simulacra_cli --test golden_pixels -- --ignored   # also the frame hashes in PIXELS (the files stay in $DIR even if a hash differs)
sh core/cli/tests/golden.sh bless core/target/release/simulacra   # rewrite SHA256SUMS; SIMULACRA_BLESS=1 on the pixel test rewrites PIXELS (order: TESTING.md, "Golden hashes")
sh core/cli/tests/golden_selftest.sh   # golden.sh against a stub binary
cargo run --release $M -p simulacra_engine --example bench -- --width 640 --height 480 --phase 0.37 --repeat 3   # scene and shading time per style
hyperfine --warmup 1 'core/target/release/simulacra --style ink --width 1920 --height 1080 --out /tmp/ink.png'   # whole runs (or a `time` loop)
core/coverage.sh   # Rust coverage as CI collects it: needs cargo-llvm-cov and llvm-tools-preview; writes lcov.info and runs core/check_lcov.sh
```

Measure performance against a fresh run of `main` on the same machine, not old numbers. Do not commit generated images.

## CI

- **Tests (`.github/workflows/tests.yml`):** every push to main and every pull request, forks included (no secrets): `cargo test` plus Clippy with `-D warnings`, for the workspace and then the engine alone, plus the portable fixtures (`--features json`); and a `golden` job: `golden_selftest.sh`, then `golden.sh check --keep` against a release binary and the `golden_pixels` test on that directory.
- **SonarQube Cloud (`.github/workflows/sonarqube.yml`, `sonar-project.properties`):** runs `core/coverage.sh` (cargo-llvm-cov, installed by `taiki-e/install-action`, with `llvm-tools-preview`) in one step, since it sources `cargo llvm-cov show-env` into its own shell (its output is shell-quoted, so it must not be copied into `$GITHUB_ENV`). It runs the workspace tests and the engine with `json` in the dev profile (`cargo llvm-cov report` reads one profile directory; the CLI integration tests run the instrumented binary Cargo builds for them), writes `lcov.info` and runs `core/check_lcov.sh`, which fails on a malformed `DA` line, on no hits for `let args = Args::parse();` in `main()` of `core/cli/src/main.rs` (only the binary runs it), or on no hits under `core/engine/src/styles`, so a collection that silently stopped contributing cannot just lower the figure. New code is held to the quality gate's 80% coverage. `sonar.sources` lists the crates' `src` directories (add a new crate there), and `core/engine/src/palettes.rs` is excluded from duplicate detection (`sonar.cpd.exclusions`), since its rows of tuples failed the duplication gate. The scan needs `SONAR_TOKEN` and skips pull requests from forks. SonarQube's Automatic Analysis must be off, because it conflicts with CI analysis.
- **Release binaries (`.github/workflows/release-binaries.yml`):** builds with `cargo install --locked --path core/cli` (the README's install command, from a checkout) for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` and `x86_64-pc-windows-msvc` (macOS is not a target: there is no Mac to test on), each on a native runner that also runs the portable fixtures and the CLI tests, on pushes to main and pull requests that touch `core/` or the workflow, and by hand. A `verify` job downloads each package (tar.gz, or zip on Windows) on a fresh runner and runs `golden.sh check` on it, so every target renders the same images; on Linux the binary runs in a pinned `debian:trixie-slim` image without a Rust toolchain. On branches and pull requests nothing is published; the packages are artifacts kept 14 days. A pushed `v*` tag also runs a `tag` job (the tag must be `v` plus the version in `core/Cargo.toml`, on a commit on main) and, once every target verified, a `release` job that renames the packages `simulacra-<version>-<target>.<ext>`, checks that the Linux binary's `--version` prints the version, writes `SHA256SUMS`, attests build provenance (`actions/attest`) and creates a draft release with generated notes; see "Releasing".
- **OSV-Scanner (`.github/workflows/osv-scanner.yml`):** scans `-r ./`, which finds `core/Cargo.lock`. Pull requests and merge groups use the PR workflow; pushes to main, a weekly schedule and manual runs use the full scan. Results are uploaded to GitHub code scanning, except for pull requests from forks, whose tokens cannot write security events, and merge groups, whose scan compares the commit with itself (the PR workflow reads `GITHUB_BASE_REF`, which GitHub sets only for pull requests).
- Actions are pinned by commit SHA with the version in a comment.

## Releasing

Releases are drafted by `release-binaries.yml` from a `vX.Y.Z` tag; nothing is public until the owner publishes the draft. Pushing a tag and publishing are outward-facing: do either only when the owner asks.

1. In a PR, set `version` under `[workspace.package]` in `core/Cargo.toml` (both crates inherit it, and `simulacra --version` prints it) and update `core/Cargo.lock` (`cargo update --workspace --manifest-path core/Cargo.toml`, which changes only the two workspace entries' versions). Merge it.
2. Tag the merge commit on main and push the tag: `git tag -a vX.Y.Z -m "simulacra vX.Y.Z" origin/main && git push origin vX.Y.Z`.
3. The workflow builds, tests and golden-checks every target, then drafts the release with the three packages, `SHA256SUMS` and generated notes. A failure creates no release; fix it, delete the tag (`git push --delete origin vX.Y.Z`, `git tag -d vX.Y.Z`) and tag again.
4. Review the draft (notes, assets), run the clean-machine checks in [`TESTING.md`](TESTING.md), and publish it. The release title and tag message are lowercase (`simulacra vX.Y.Z`), like the binary and package names. Anyone can check a download with `gh attestation verify FILE --repo juusolatva/simulacra`.

## Architecture

- **Registry:** the engine's `for_each_style!` macro in `core/engine/src/lib.rs` is the one list of styles: it generates `STYLES` and the scene deserialization. `scene_builders!` in `core/engine/src/scenes.rs` lists each style's scene struct and generates `SCENE_BUILDERS` (alphabetical; the binary's `--style` choices and `--list-styles`), `build_scene` and `build_scene_json`.
- **Scenes and shaders:** a scene struct implements `BuildScene::build(&SceneParams)` (width, height, the full 64-bit seed, the palette, the phase), which makes all of the style's random draws, and `Style::render(width, height, seed32, palette)`, which shades rows in parallel (rayon) and returns packed RGB bytes. Shaders take the 32-bit `seed32(seed)` (`seed as u32`). Shared helpers `circle_offset`, `golden_start` and `ROUGH_TAU` (`6.28`, not tau) live in `styles/mod.rs`, with `gaussian`, `unit`, `center` and `small_side`; `geometry.rs` holds `py_mod`, `py_sum`, and polygon and segment distances.
- **Randomness:** `simulacra_engine::PyRandom` (`core/engine/src/random.rs`) reproduces CPython's `random.Random` for `i64` seeds draw for draw (MT19937 seeding, `random`, `uniform`, `randint`, single-argument `randrange`, `choice`, `getrandbits` up to 128 bits), so every seed keeps its scene. `core/engine/tests/random_reference.json` holds CPython sequences that `tests/py_random.rs` replays. Use only those methods; a new one must reproduce CPython's draws (derive per-item values from the index instead where possible). The number and order of draws are part of the output: `orbits` draws `randrange(n_stops)`, so the palette's stop count affects its scene.
- **Exact arithmetic:** the shaders and builders keep their arithmetic operation for operation, and the fixtures and golden hashes depend on it: no algebraic rewrites, no `mul_add` outside the error-free products in `py_hypot`, no `clamp` where `max`/`min` NaN behavior differs, a float power as `m_powf` (not `powi`), rounding as `round_ties_even`, truncation as a cast, float modulo as `geometry::py_mod` (floored, CPython's `%`), compensated sums as `geometry::py_sum`, and `(distance, value)` tuple ordering where ties matter (see `Voronoi`). Threshold and first-hit styles (contour lines, `asteroids`, `marbling`, `voronoi` ties) can change visibly from a one-ulp difference. Comments describe the behavior itself; the `py` prefix (`PyRandom`, `py_mod`, `py_sum`, `py_hypot`) marks code that reproduces CPython bit for bit.
- **Libm:** call transcendental functions through the `Libm` trait in `core/engine/src/math.rs` (`x.m_exp()`, `m_sin`, `m_cos`, `m_tan`, `m_tanh`, `m_atan`, `m_atan2`, `m_powf`, `m_ln_1p`), never the `f64` methods (`core/clippy.toml` forbids them outside `math.rs`). The trait calls the pure-Rust `libm` crate, so every platform renders the same image and the fixtures and golden hashes hold everywhere. The platform libm was measured at only 1 to 11% faster over all styles (the crate's `pow` is 2 to 3.4 times and `exp` 1.7 to 1.9 times slower per call), not worth a second backend whose images differ. `math::py_hypot(x, y)` is an exact port of CPython's `hypot`; `f64::hypot` is forbidden as well. A faster shader should call `pow` and `exp` less, which changes its images (a deliberate visual change).
- **Noise:** `fbm()` returns values in `[0, 1]` centered near 0.5. Do not treat it as `[-1, 1]` (`n * 0.5 + 0.5` is wrong). Use `contrast(n, gain)` to stretch it, and `polar_noise()` for anything indexed by an angle, because raw `theta` creates a seam at ±π. `fbm()` uses the same seed for every octave, so octaves are correlated at the lattice points; changing that would alter every noise-based style.
- **Looping noise:** `fbm_loop` blends a stack of ordinary 2D noise layers, each the same noise under the seed plus `7919 * layer`. Layer 0 is the real seed, so phase 0 is exactly the still noise, and the layer index wraps, so phase 1 repeats phase 0. Octave `i` steps through `NOISE_LAYERS + i` layers per loop so the octaves do not all stall or pulse together. The blend is linear on purpose; an eased blend varied the speed about 3x and hitched at the loop point. A style animates its noise by putting the phase in its scene for the shader; a looping-noise phase is validated by `check_loop_phase` (finite only) since huge phases are reduced by the noise.
- **Animation:** every style moves. A builder adds `loop_angle(phase, k)` (`tau * k * (phase % 1.0)`, `k` a whole number, negative to reverse) to phases and angles, or circles positions with `circle_offset()` (exactly zero at phase 0), without new random draws, so phase 0 is the still image and phase 1 repeats it. Offsets that are not whole turns (the drift in `voronoi`) are measured from their starting value so phase 0 adds exactly 0.0. Brush and trail styles move their scene data (comet, ember, flowfield starts, ink control points, constellation stars via `drift_stars`; constellation pairs are chosen from the starting positions so the line set stays constant), and `lissajous` turns its curve phases. `torus` rotates its model points (an exact identity at angle 0) and takes the depth range from the turned knot but the centre and scale from the unturned one; `quasar` adds a loop to the jet's spin; `mandala` counter-rotates ring and spoke phases; per-ring turbulence in `quasar` and `mandala` stays fixed. `mandelbrot` gets `scale`, `center` and `iterations` from its scene: the zoom is `exp(-depth * ease)` with a cosine ease, the centre moves with `1 - closing`, and phase 0 is exactly the original view; it ignores the seed. Shards turn with `turned_about`, which adds the offset to the point. The binary's frame phases are `frame_plan` in `core/cli/src/main.rs`: `py_mod(phase, 1.0) + i / frames`, or consecutive seeds with `--slideshow`.
- **Brush and trail styles** (torus, lissajous, constellations, ink, flowfield, comet, ember, attractor; `core/engine/src/styles/brush.rs`) stamp sequentially in a fixed order into a shared buffer and then shade in parallel, since float addition order changes results. `sample_by_length` samples the torus and lissajous curves at a spacing tied to the glow width.
- **Attractor:** parameters come from `ATTRACTOR_TABLE` in `brush.rs` (256 sets, mirrored on one random bit), chosen with integer draws only, so no libm changes a seed's figure. It counts integer hits, so order does not matter, but its orbit is chaotic, which is why its point-density noise depends on the libm. The table's doc comment lists the offline checks every entry passed; add entries only with the same checks.
- **Marbling** undoes its ops (drops and combs, each exactly invertible) from last to first per pixel, so scene order is the order they were applied; drops circle and comb strength is scaled by `cos(loop_angle(...))`.
- **Space styles** (`space.rs`): distances use `sqrt(dx * dx + dy * dy)` rather than `hypot`. `lunar` marches a soft shadow through its analytic crater height field; `asteroids` shades rocks nearest first and takes the first hit; `blackhole` maps the sky through `1 - 1.6 / r**2` to fake lensing; `supernova` evolves its filaments with looping noise.
- **Woodblock** samples animated hill, cliff and wave silhouettes per column in canvas-relative units and shades overlapping layers and carved contour grooves; the final palette stop is paper. `watercolor` is a palette, not a filter.
- **Mosaic** computes one palette position per tile on a grid about `MOSAIC_TILES` tiles across the short side, so the work does not grow with the canvas, and the shader only expands tiles and grout to pixels. Its noise is sampled in tile units (`value_noise` has an 8-unit cell, so scales near 1). Patterns move by whole tiles, wrapping after one period per loop.
- **Scene validation (`core/engine/src/validate.rs`):** every `Style` implements `validate(&Canvas) -> Result<f64, SceneError>`, which checks the scene and returns its estimated work; the checked `simulacra_engine::render` calls `validate_scene` before shading, and the binary renders through it (`Style::render` itself is unchecked). Every float field goes through `check_numbers!` (finite, at most 2**40), except a looping-noise phase (`check_loop_phase`); indices and lengths are checked against the canvas, the palette and each other; a style that allocates a canvas-sized buffer per item caps the count (`lissajous` 8 curves, `horizon` 64 layers); and the work estimate counts inner-loop iterations per pixel, with sequential steps weighted by `SEQUENTIAL_WEIGHT` and attractor steps by `ATTRACTOR_STEP_WORK`, against `work_limit()` (2**27 + 16384 per pixel, roughly 20 to 30 s of rendering at 4K on 12 threads). When a style gains a field or a loop, update its `validate` in the same change: `every_scene_number_is_range_checked` (`core/engine/tests/validation.rs`) sets each fixture number to 1e300, and `scenes_stay_well_within_the_work_limit` (`invariants.rs`) holds built-in scenes to an eighth of the limit at sizes up to 4K.
- **Portable fixtures (`core/engine/tests/fixtures/`):** one JSON file per style: a scene at 48×36, seed 3, phase 0.37 and a palette cycling through the built-ins, with the SHA-256 of the packed RGB it renders. The committed scenes still have the key order and number format they were first written with, so the first bless of one rewrites every line. `fixtures.rs` renders them (exact hashes), builds each scene from scratch with `build_scene`, and requires one fixture per style. The ignored `bless_fixtures` test rewrites only a fixture that is missing, does not parse, holds a scene that no longer deserializes or validates, or whose built scene renders another hash (with sorted keys and `serde_json` number formatting), and leaves the rest byte for byte. Scenes load through serde (`scene_from_json`, feature `json`, with `serde_json`'s `float_roundtrip`, which must stay on). JSON is for generated files only; hand-edited data should use TOML or YAML.
- **Golden hashes (`core/cli/tests/golden/`):** `workloads.txt` (hand-edited) lists output names and the binary's arguments; a line holding `{style}` is expanded for every style in `--list-styles`. `SHA256SUMS` holds each output file's SHA-256 and `PIXELS` each decoded frame's (`name#frame`). `golden.sh` (POSIX sh, also under Git Bash and in the clean container) requires the workload and manifest names to be the same set before comparing hashes; `golden_pixels.rs` decodes with the test decoders in `core/cli/tests/common/`, also requires the `fixture-<style>.png` frames to hash as the portable fixtures, and blesses `PIXELS` only from a complete directory whose files match `SHA256SUMS` and whose fixture frames match the fixtures. An encoder-only change (a `flate2` or `miniz_oxide` update) re-blesses `SHA256SUMS` alone, after the pixel test passes against the unchanged `PIXELS`; a deliberate visual change re-blesses the fixtures, then `SHA256SUMS`, then `PIXELS` (steps in `TESTING.md`), and the diff shows which workloads changed.
- **Binary (`core/cli`):** options with clap (`args_override_self`, so a repeated option takes its last value), the engine's palette table (`palettes.rs`), the checked `render`, its own PNG and APNG writer (`png.rs`, `flate2` at level 9 with filter None; `Apng::compress` compresses a frame on any thread and `Apng::frame` returns its chunks in order), its own GIF writer (`gif.rs`: 240 palette samples plus 16 greys shared by all frames, nearest entry cached per 5-bit colour cell, a variable-width LZW encoder whose width growth mirrors the decoder, delays in whole hundredths, at least 2), and an atomic write (`output.rs`: a temporary file created with mode 0o666, so the umask applies, then a rename; `atomic_write_with` lets frames go to disk as they finish). Animations render and encode whole frames as jobs on Rayon's pool (`in_order`), at most `frames_in_flight` at once (one per thread, within `FRAMES_IN_FLIGHT_BYTES`, 1 GiB by `frame_bytes`: `FRAME_BYTES_PER_PIXEL`, 32, and `FRAME_BYTES_PER_SIDE`, 320 per pixel of width + 2 × height, both sized for `lissajous`, the most memory-hungry style; raise them if a style needs more), written in frame order, so the first failing frame's error is reported. Limits (`check_limits`, before rendering): `MAX_FRAME_PIXELS` (100 M), `MAX_SIDE` (100,000, because some scenes grow with a side alone and are built before validation), `MAX_TOTAL_PIXELS` (2**32 pixels in all frames, for run time and output size) and `MAX_FRAMES` (65,536, for the fixed cost of each frame); `--no-limits` skips them, but more than 2**31 APNG frames and GIF sides over 65,535 are refused as format limits. Exit status 2 for refused arguments and limits (`Failure::Usage`, including the `--slideshow` seed overflow), 1 for a failure while rendering or writing (`Failure::Runtime`).
- **Colors:** palette stops are sRGB, and the writers store samples unchanged. Do not introduce a linear-to-sRGB conversion. Every built-in palette has at least 5 stops and a dark first stop (every channel below 64), since many styles take their background from it; `palettes.rs` is sorted by name.

## Conventions

- **Size independence:** express shape sizes, radii, wave frequencies and noise scales relative to the canvas (`min(width, height)` or `max(width, height)`), not in pixels. Keep wave frequencies well below Nyquist (π radians per pixel). `invariants.rs` checks palette range, aliasing and canvas scaling.
- **Brightness:** prefer `1 - exp(-k * v)` tone mapping over dividing by a fixed count, which leaves styles nearly black. Every style must span more than 0.5 of its palette at 64×64 (`every_style_uses_a_wide_palette_range`).
- **Changing a style's output:** the fixtures and golden hashes are the only reference. A deliberate change re-blesses the style's portable fixture (`bless_fixtures`) and both golden manifests in the same PR, and the PR shows before-and-after renders (see [`TESTING.md`](TESTING.md)). An accidental change fails the fixture tests and the golden check.
- **Behavior-preserving refactors:** the golden check, the pixel test and the fixtures must pass unchanged.
- **Adding a style** (none planned for now): a scene struct in `core/engine/src/styles/` with `Style::render` and `Style::validate`, a `BuildScene::build` drawing everything through `PyRandom` and moving with the phase without new draws, one line in each of `for_each_style!` and `scene_builders!`, a blessed fixture, a `fixture-<style>.png` line in `core/cli/tests/golden/workloads.txt` and blessed golden hashes (its `{style}` workloads fail until then), the style count in `invariants.rs` (`SCENE_BUILDERS.len()`) and the README, and a row in the README style table. A new built-in palette goes into `core/engine/src/palettes.rs` (sorted) and the README palette table.
- **Start from `origin/main`:** several sessions work on this repository in parallel, so run `git fetch` and `gh pr list` before starting and branch from `origin/main`; a local `main` can be several PRs behind.
- **New crate versions:** pin releases at least two weeks old (check the crates.io release date; pin in `Cargo.lock` with `cargo update -p <crate> --precise <version>` when a newer release is too fresh), and look up unfamiliar transitive crates before committing the lockfile.

## SonarQube and CodeQL triage notes

Project key: `juusolatva_abstract-art` (the project's former name).

- **Atomic-write mode (`core/cli/src/output.rs`, 0o666):** if a scanner flags the permissive mode, it is a false positive. 0o666 is the mode an ordinary file creation passes; the kernel removes the umask bits, so the file gets the permissions of any new file (0o644 under the usual umask 0o022), which `new_files_get_the_umask_default_mode` checks. A fixed stricter mode would override a user's umask, and reading the umask means changing it process-wide. Dismiss as a false positive.
- **rust:S6164 (approximate constant, e.g. `1.414` read as `SQRT_2`) in `ATTRACTOR_TABLE`:** false positive. The table entries are parameter values that must stay exactly as they are; a library constant would change the figure.
- **Re-raised findings:** moving or renaming code makes SonarQube report the same finding again at the new location. Triage it the same way, noting in the comment that the code moved.
- **Workflow with PRs:** SonarQube Cloud (CI analysis) runs on every PR. The other review tools (bots and GitHub apps) change over time, so check which ones reported on the PR rather than expecting a fixed set. Fix valid findings and answer each one, naming the commit or explaining why nothing changed: on its review thread, or in a PR comment for a tool that posts all its findings in one comment. The user resolves threads. Check claims about library APIs against current documentation before changing code; review bots can describe older versions.

## Known issues and follow-ups

Open work, none started:

- **Windows signing:** check what SmartScreen shows for a downloaded `simulacra.exe` and decide whether to sign the Windows binaries.
- **Clean-machine check:** run a downloaded release on a clean Windows machine or VM (no Rust, no Python); Linux is covered by the verify job's clean container. Steps in [`TESTING.md`](TESTING.md).
- **Linux glibc baseline:** the Linux binaries link the glibc of the build runner (Ubuntu 24.04); decide the oldest glibc to support, or build static musl binaries instead.

- **Turbulence:** animate the per-ring turbulence in `quasar` and `mandala`, which needs the noise to take a phase.
- **Parallel stamping:** brush stamping could be parallelized (one band of rows per thread, each replaying all stamps in order) if `ink` at very large sizes matters.

### Rendering quirks (not bugs, but worth knowing)

- **Mandelbrot:** ignores the seed by design; only `--slideshow` gives identical frames.
- **Comet length:** comet length scales with the width only, so trails are short on tall canvases.
- **Cosmic arm:** the arm in `cosmic` is placed along a straight ray, so it is not really curved.
- **Attractor collapse:** periodic windows are dense in a chaotic map, so roughly one 60-frame `attractor` animation in 250 may show one frame where the figure collapses to a few cells.
- **Pixel-based sizes:** some features are still measured in pixels: star dots in `orbits`, `nebula` and `constellations`; brush and ember widths in `ember` and `comet`; and pixel-scaled noise in `waves`, `orbits`, `interference`, `bloom`, `torus`, `pinwheel`, `galaxy` and `quasar`. Their detail changes with resolution.
- **Culling:** skips happen only where a contribution is exactly zero (row filtering of stars and glyphs, exact-zero ring bands in `mandala`, column bounds in `ember`, bounding-box pruning of segments in `circuit`), either from a hard cutoff or because `exp()` underflows past `GAUSSIAN_ZERO` standard deviations; any other skip would change the images.
